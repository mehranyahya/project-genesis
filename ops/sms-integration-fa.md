# زیرساخت پیامک — آماده‌سازی با پیش‌فرض خاموش

تاریخ: ۲۰۲۶-۱۰-۲۰. محدودهٔ مصوب این بسته آماده‌سازی اتصال پنل است؛ سرویس‌دهنده هنوز انتخاب نشده است. هیچ کلید واقعی، ارسال واقعی، خرید، Deploy یا Migration آنلاین در این بسته انجام نشده است.

## چه چیزی آماده است؟

| بخش | رفتار |
| --- | --- |
| قرارداد پنل | `supabase/functions/_shared/sms-provider.ts`؛ Adapter اختصاصی و قابل‌تعویض، با نتیجهٔ محدود و صریح |
| ارسال‌کننده | `sms-delivery.ts`؛ کنترل تنظیمات، اعتبارسنجی Claim، مجوز پیش از ارسال، تکمیل و آمار بدون دادهٔ مشتری |
| ثبت اولیه | فقط بعد از `REQUEST_CREATED`، به‌صورت Background با `EdgeRuntime.waitUntil`؛ پاسخ ثبت منتظر پنل نمی‌ماند |
| بازیابی | در همان Edge Function ساعتی `telegram-recovery`؛ امضا/Nonce موجود حفظ شده، صف و شکست دو کانال مستقل‌اند |
| ذخیرهٔ پایدار | Migration آمادهٔ `20261020034952_add_disabled_sms_outbox.sql`؛ هنوز آنلاین اعمال نشده |
| ایمنی هزینه | سقف تلاش‌های رزروشده در ۲۴ ساعت، برای هر شماره در ۲۴ ساعت و در ساعت؛ شامل Retry و ارسال نامطمئن |
| حریم خصوصی | صف، شماره/نام/توضیح/متن آزاد/کلید پنل را کپی نمی‌کند؛ شماره فقط هنگام مجوز از درخواست خوانده می‌شود |
| پشتیبان | Manifest بازیابی، وجود کامل جدول‌ها و RPCهای پیامک را پس از نصب کنترل می‌کند؛ با DB قبل از این Migration سازگار است |

هدف آماده‌شده **رسید کوتاه ثبت درخواست** برای هر سه خدمت است. OTP، تأیید مالکیت شماره، ورود مشتری، پیام تبلیغاتی، ارسال دستی انبوه و تغییر وضعیت سفارش جزو این بسته نیستند. اعتبارسنجی فرمت `+989…` به معنی تأیید مالکیت شماره نیست.

## وضعیت خاموش و مرز اتصال پنل

در Edge runtime مقدار `SMS_DELIVERY_ENABLED` اگر غایب/خالی/`false` باشد، پردازش پیامک پیش از هر RPC یا فراخوانی پنل تمام می‌شود. فقط مقدار دقیق `true` بررسی فعال‌سازی را شروع می‌کند. `SMS_PROVIDER_ID` باید با Adapter ثبت‌شده در کد برابر باشد.

اکنون `resolveSmsProvider` برای همهٔ نام‌ها `null` می‌دهد. هیچ Provider واقعی یا Mock قابل‌انتخاب از Env وجود ندارد. بنابراین **افزودن API Key به‌تنهایی ارسال را فعال نمی‌کند**. تنظیم فعال بدون Adapter، `unconfigured` می‌شود و بازیابی ساعتی خطای عمومی ۵۰۳ می‌دهد؛ کلید یا متن خطای پنل منتشر نمی‌شود.

حتی پس از افزودن Adapter، `sms_delivery_policy.enabled=false` در DB کلید توقف مستقل است. این Policy، ثبت درخواست را متوقف نمی‌کند؛ `request_rate_limit_policy` و Gateهای قبلی ثبت درخواست جدا هستند. خاموش‌کردن Policy قبل از ارسال بعدی دوباره بررسی می‌شود؛ درخواست شبکه‌ای که قبلاً شروع شده قابل پس‌گرفتن نیست. خاموش‌کردن Env جلوی Claimهای بعدی را می‌گیرد؛ برای توقف کارهای رزروشده، Policy دیتابیس نیز خاموش شود.

Secretهای پنل فقط در Supabase Edge secret storage قرار می‌گیرند. هیچ Secret پیامک، `SMS_*` یا آدرس قابل‌تنظیم پنل وارد Browser، `VITE_*`، Build یا Worker نمی‌شود. هیچ Route عمومی جدیدی برای ارسال پیامک ایجاد نشده است.

## قرارداد داده و زبان

پس از فعال‌سازی تأییدشده، Trigger همان تراکنش `requests` فقط برای درخواست دارای Bot verification معتبر و شمارهٔ استاندارد، یک رکورد با کلید یکتای `request_id` می‌سازد. Replay یا فعال‌سازی بعدی، درخواست‌های قدیمی را دوباره صف نمی‌کند. این رفتار مانع موج پیامک تاریخی هنگام روشن‌کردن سرویس می‌شود.

Locale از Hash سند شرایط پذیرفته‌شده تعیین می‌شود: `fa_terms_hash` و `en_terms_hash` در Policy باید از دو سند واقعی و مصوب همین انتشار پر شوند؛ قالب‌های مستقل `fa_template_id` و `en_template_id` نیز لازم‌اند. استفاده از Hash ناشناخته/قدیمی فقط پیامک را حذف می‌کند و ثبت معتبر درخواست را خراب نمی‌کند. بعد از تغییر شرایط، هم‌زمانی این دو Hash با انتشار جدید باید بررسی شود. این نگاشت تنها Hash فعلی هر زبان را پوشش می‌دهد؛ Hashهای قدیمی مجاز Terms به‌طور خودکار به پیامک نگاشت نمی‌شوند.

هر Job، شناسهٔ Provider، نسخه/شناسهٔ قالب و Locale خود را ثابت نگه می‌دارد. تعویض پنل یا قالب، مجوز ارسال رزروشده با مشخصات قبلی را لغو می‌کند؛ آن Job با پنل جدید به‌طور خودکار بازپخش نمی‌شود.

Payload تحویلی به Adapter فقط شامل رویداد `request_received`، شماره، Locale، شناسهٔ قالب، `{tracking_code}` و کلید ثابت `receipt:<request_id>` است. اطلاعات مزار، نام، شهر، محل، مبلغ یا یادداشت مشتری ارسال نمی‌شود.

متن‌های زیر **پیشنهاد برای تأیید مالک و ثبت قالب در پنل** هستند، نه محتوای منتشرشده یا قالب تأییدشدهٔ سرویس:

- فارسی: «درخواست شما ثبت شد. کد پیگیری: {tracking_code}»
- انگلیسی: “Your enquiry has been recorded. Reference: {tracking_code}.”

نام برند یا لینک پیگیری ساخته نشده است. متن، نوع خط/الگو، اجازهٔ ارسال خدماتی و پشتیبانی Unicode باید با پنل منتخب و محتوای واقعی بررسی شوند.

## صف، تلاش مجدد و نتیجهٔ نامطمئن

سه جدول خصوصی با RLS فعال و اجباری ساخته می‌شود: `sms_delivery_policy`، `sms_outbox` و `sms_delivery_attempts`. دسترسی مستقیم PUBLIC/anon/authenticated/service_role به این جدول‌ها بسته است. سه RPC محدود Claim/Authorize/Complete فقط مجوز اجرای `service_role` دارند؛ Trigger برای مصرف عمومی قابل‌اجرا نیست. Functionها `search_path=pg_catalog` دارند.

Claim حداکثر ۵ Job می‌گیرد؛ Immediate حداکثر یکی. قفل تراکنشی Policy، بودجهٔ مشترک تمام Claimها را هماهنگ می‌کند و `FOR UPDATE … SKIP LOCKED` رکورد صف را رزرو می‌کند. هر رزرو Attempt و Lease token تازه دارد. شبکه بعد از Commit و خارج از قفل DB اجرا می‌شود. حداکثر دو ارسال هم‌زمان در هر Batch، Timeout پنل ۸ ثانیه و Lease دو دقیقه است.

بودجهٔ اولیه محافظه‌کارانه است: ۲۰ رزرو در ۲۴ ساعت برای کل سایت، ۲ برای هر شماره در ۲۴ ساعت و ۱ در ساعت. این اعداد تنظیم قابل‌بازبینی هنگام فعال‌سازی‌اند؛ ظرفیت یا هزینهٔ واقعی پنل نیستند. رزرو از بودجه کم می‌شود حتی اگر Worker قبل از ارسال متوقف شود. تعداد Segment، تعرفه، شارژ و محدودیت واقعی پنل بعد از انتخاب باید جدا بررسی شوند؛ این شمارنده سقف ریالی تضمین نمی‌کند.

| نتیجه | رفتار |
| --- | --- |
| `accepted` همراه Receipt معتبر | ثبت `accepted`؛ به معنی پذیرش پنل است، نه تحویل قطعی به گوشی |
| `retryable` مستند | فقط وقتی Adapter از پاسخ مستند پنل می‌داند پیام **پذیرفته نشده**؛ حداقل ۵ دقیقه و سپس ۳۰ دقیقه، با رعایت Retry-After و بودجه |
| `permanent_failure` | پایان در `failed` |
| Timeout، Exception، نتیجهٔ بدشکل یا مبهم | `uncertain`؛ بدون ارسال مجدد خودکار |
| Lease منقضی‌شده پس از Crash/قطع پاسخ | `uncertain`؛ ممکن است پنل پیام را پذیرفته باشد |
| پایان عمر | Receipt پس از ۲۴ ساعت `expired` می‌شود؛ سقف کلی حداکثر سه تلاش است |
| شماره حذف/ناشناس‌شده، Spam، توقف یا تغییر تنظیمات | لغو پیش از تماس بعدی با پنل |

HTTP ۴۲۹ یا ۵xx به‌تنهایی مجوز Retry نیست. مستندات پنل باید عدم پذیرش را روشن کند. کلید ثابت Idempotency فقط وقتی مانع تکرار سمت پنل می‌شود که خود پنل آن تضمین را مستند و پیاده‌سازی کرده باشد؛ این بسته ادعای Exactly-once ندارد.

کار `uncertain` یا `failed` خودکار دوباره صف نمی‌شود. ابتدا باید وضعیت همان Receipt/کلید در پنل بررسی شود؛ بازپخش بدون آشتی‌دادن وضعیت ممنوع است. API استعلام/Callback تحویل، امضا و قرارداد آن بعد از انتخاب پنل نوشته می‌شود؛ اکنون Webhook عمومی یا تأیید تحویل ساختگی وجود ندارد.

برای پایش اولیه فقط آمار بدون شناسه/مشتری بخوانید؛ از چاپ Row یا پاسخ خام پنل پرهیز شود:

```sql
select state, count(*) from public.sms_outbox group by state order by state;
select count(*) as reserved_last_24h from public.sms_delivery_attempts
where reserved_at > clock_timestamp() - interval '24 hours';
```

## آزمون و محدودیت شواهد

`src/lib/sms-delivery.test.ts` کد واقعی پردازش و Entryهای واقعی Submit/Recovery را با وابستگی‌های آفلاین آزمون می‌کند: خاموش‌بودن، نبود Adapter، دو زبان، دادهٔ حداقلی، Lease، نتیجهٔ مبهم، خطای تکمیل، جدایی دو کانال و شکست پیامک پس از ثبت موفق.

`src/lib/sms-outbox.sql.test.ts` کل SQL آماده‌شده را با ۲۰ سناریو در PostgreSQL مبتنی بر PGlite داخل فرایند Node جدا اجرا می‌کند. Wrapper علاوه بر Exit code، پایان کامل TAP و ۲۰ Pass/صفر Fail را لازم می‌داند. PGlite `0.3.14` فقط Dev dependency است؛ هیچ Import تولیدی یا Browser ندارد. اجرای مستقیم:

```sh
node --test --test-reporter=tap scripts/check-sms-outbox.mjs
bun test src/lib/sms-delivery.test.ts src/lib/sms-outbox.sql.test.ts
```

این آزمون DB از Fixture حداقلیِ مرز `requests` استفاده می‌کند؛ جایگزین اجرای کل تاریخچهٔ Migration، RLS/Advisor و Restore در Supabase واقعی نیست. PGlite تک‌اتصال است؛ Claimهای متوالی و State/ACL آزموده شده‌اند، نه رقابت واقعی چند اتصال. آزمون هم‌زمانی واقعی دو Worker و پنل منتخب در Preview باز می‌ماند.

خروجی Build مرورگر باید با شواهد نسخهٔ پایه مقایسه شود. مستقل‌بودن صف و Background به معنی تضمین صفر میلی‌ثانیه سربار نیست: پس از نصب و فعال‌سازی، خواندن Policy و درج Outbox بخشی از تراکنش DB می‌شود. درصد افت سرعت بدون اندازه‌گیری واقعی اعلام نمی‌شود.

## ترتیب اتصال پس از انتخاب پنل

۱. نام پنل و مستندات رسمی API، روش احراز هویت، خط/Template ID هر زبان، پذیرش Unicode، کدهای خطا، محدودیت‌ها، Idempotency و استعلام/تحویل مشخص شود. کلید واقعی از مسیر Secret storage وارد شود، نه گزارش یا Git.

۲. Adapter اختصاصی در همین مرز Server نوشته و به Registry ثابت اضافه شود. `postSmsJson` برای پنل JSON، HTTPS/Origin ثابت، POST، عدم Redirect، Timeout و پاسخ محدود ۱۶KiB را فراهم می‌کند؛ برای پنل SOAP/غیرJSON باید Transport مناسب با همین حدود نوشته شود. URL/Host پنل از درخواست کاربر یا Env دلخواه گرفته نشود. هیچ تبدیل عمومی ۵xx→Retry نوشته نشود.

۳. پس از Backup رمزنگاری‌شده، Checksum و Restore drill مطابق [قرارداد پروژه](../AGENTS.md) و [راهنمای بازیابی](supabase-backup-restore.md)، Migration فقط در Preview مستقل اعمال و RLS/ACL/Advisor، Trigger اتمیک، دو Claim هم‌زمان، Budget و Restore بررسی شود. Policy پیامک و ثبت درخواست در پیش‌آزمون خاموش می‌مانند.

۴. قالب و اطلاع‌رسانی حریم خصوصی دو زبان تأیید شود، Provider/Template/Hashهای واقعی تنظیم شوند، Secretها فقط در Edge قرار گیرند و Adapter با پاسخ‌های مصنوعی شامل Timeout و پذیرشِ قبل از قطع پاسخ آزموده شود.

۵. فقط در پنجرهٔ صریحاً مجاز Preview، با بودجهٔ کم و شمارهٔ متعلق به مالک/آزمونگر، E2E اجرا شود. پذیرش پنل و تحویل گوشی جدا ثبت شوند؛ خطر ارسال تکراری پس از Timeout و قطع DB آزمایش شود. پس از پنجره، هر دو کلید توقف خاموش شوند. Production فعال‌سازی مستقل می‌خواهد.
