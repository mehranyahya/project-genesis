# Project Genesis — Cloudflare Deployment Runbook

Status: pre-production. This runbook is operational guidance; it does not authorize a deployment.

## Non-negotiable rules

- Cloudflare delivery is manual only through `.github/workflows/deploy-cloudflare.yml`.
- No push or pull-request event may publish a Worker.
- Preview uses `wrangler versions upload` and must not be promoted automatically.
- Production uses `wrangler deploy` only from `main` and only with the exact manual confirmation `DEPLOY_PRODUCTION`.
- Never paste production secrets into chat, commit them to Git, or expose them through `VITE_*` variables.
- `DEPLOY_TARGET` and `PUBLIC_INDEXING` are non-secret Wrangler vars generated by the deploy pipeline; they are not manually stored as runtime secrets.
- The PostgreSQL request rate-limit policy remains disabled until the preview request-flow gate is explicitly approved.
- SMS provider integration is deferred and is not a launch-foundation dependency. No SMS secret is required by the current deploy workflow.

## Current production blockers

Production deployment is **BLOCKED** until all of these are closed:

1. CSP is implemented with a framework-compatible nonce/hash strategy and verified against TanStack hydration plus Cloudflare Turnstile. Do not weaken this gate with a permanent `unsafe-inline` shortcut.
2. The final public domain/canonical origin is fixed and the production sitemap is generated and tested. Do not invent a placeholder production domain.
3. Turnstile production configuration contains the final hostname(s) and the production site/secret key pair is verified.
4. Preview smoke tests pass, then the PostgreSQL request rate-limit policy is deliberately enabled and the end-to-end request path is re-tested.
5. Final-domain HTTPS smoke passes before HSTS is enabled. Initial HSTS must start at `max-age=86400` without `includeSubDomains` or `preload`; those are later decisions.

## GitHub Environments

Create two GitHub Environments before the first workflow run:

- `preview`
- `production`

Use Environment protection rules for `production` as appropriate. The workflow additionally enforces `main` plus `DEPLOY_PRODUCTION`.

### Required Cloudflare CI credentials

Configure these as GitHub Environment secrets. They are used by Wrangler but are **not** written into the Worker runtime secret file:

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`

The API token should be scoped only to the Cloudflare resources required to upload/deploy this Worker and its configuration.

### Required build-time public value

- `VITE_TURNSTILE_SITE_KEY`

This value is browser-visible by design, but the workflow stores it through the Environment secret interface so preview and production can use different values without changing source code.

### Required Worker runtime secrets

The workflow validates these values, writes them only to a temporary `0600` JSON file, passes that file to Wrangler, and removes it with an `always()` cleanup step:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `REQUEST_FINGERPRINT_KEY`
- `REQUEST_FINGERPRINT_KEY_ID`
- `IP_HASH_KEY`
- `TURNSTILE_SECRET_KEY`
- `TURNSTILE_ALLOWED_HOSTNAMES`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_ADMIN_CHAT_ID`

`REQUEST_FINGERPRINT_KEY_ID` must remain stable while requests signed with that key ID are still inside the idempotency window.

No SMS provider key belongs in this list today.

## Preview sequence

1. Confirm `main` CI is green.
2. Configure the `preview` Environment values above.
3. Open GitHub Actions → **Deploy Cloudflare** → **Run workflow**.
4. Choose `target = preview`. Leave the production confirmation empty.
5. The workflow must run, in order: dependency install, lint, typecheck, tests, target indexing preparation, build, generated Wrangler preparation, artifact verification, runtime-secret validation, then `wrangler versions upload`.
6. Do not promote the uploaded version to production traffic as part of this step.
7. Verify the preview response has `X-Robots-Tag: noindex, nofollow, noarchive`.
8. Verify preview `robots.txt` is exactly closed with `Disallow: /` and no preview sitemap exists.
9. Smoke the main routes and request-form rendering. Verify Turnstile executes at submit time rather than blocking page load.
10. While `public.request_rate_limit_policy.enabled = false`, a brand-new request is expected to fail closed. Do not interpret that expected guard as a deployment failure.

## Request-flow activation gate

After the static/Turnstile preview smoke is clean, explicitly decide whether to enable the PostgreSQL request policy. Do not make this change implicitly from a code deploy.

When approved, verify the configured v23.2 matrix before enabling it:

- 3 committed new requests per phone / 10 minutes.
- `unverified_no_token`: 2 per phone / 30 minutes.
- `unverified_service_error`: 20 global / 60 minutes.
- `unverified_service_error`: 3 per combined `ip_hash + phone` / 60 minutes.
- shared IP 20/hour: review flag only.
- unverified shared IP 200/hour: emergency hard ceiling.
- same `phone + request_type` inside 10 minutes: review flag, not an independent hard duplicate block.
- Worker flood layer: 300 submit attempts per valid Cloudflare IP / 60 seconds; PostgreSQL remains authoritative for business limits.

Then run one controlled end-to-end request and verify:

- a single request row is committed;
- a valid `MA-…` tracking code is returned;
- immediate Telegram delivery is attempted after commit;
- Telegram failure cannot roll back or fake request failure;
- replay of the same valid submission identity returns the existing tracking code before consuming a new Turnstile verification;
- no second request row is created for that replay.

## Production sequence

Do not start this sequence while any production blocker above is open.

1. Fix the final public origin/domain and generate the production sitemap from real routes/content.
2. Verify production `robots.txt` allows the public site and includes `Disallow: /api/`.
3. Close the CSP gate with an executable `Content-Security-Policy` header and regression tests.
4. Configure the `production` GitHub Environment secrets with production values.
5. Verify Turnstile production hostname allowlist and action `submit_request`.
6. Confirm the request policy is enabled and the preview end-to-end request gate has passed.
7. Run final-domain HTTPS smoke. HSTS remains off until this succeeds.
8. Run **Deploy Cloudflare** from `main`, choose `target = production`, and type `DEPLOY_PRODUCTION` exactly.
9. Re-run smoke tests against the public domain immediately after deployment.
10. Only after stable HTTPS smoke, enable initial HSTS `max-age=86400` without `includeSubDomains` or `preload`.

## Rollback principles

- Application rollback uses Cloudflare Worker version/deployment rollback; do not rewrite Git history to roll back production.
- A Worker rollback does not roll back Supabase migrations or request rows.
- Database schema changes require their own forward-fix/rollback plan; never assume a code rollback reverses the database.
- Request creation success is authoritative only after the database commit and a valid tracking code.
- Telegram and future SMS are post-commit side effects and cannot redefine request success.

## SMS — deferred provider integration

The customer confirmation SMS provider can be connected later without blocking the current launch foundation.

Future provider rules:

- provider-specific code stays behind a server-only notification/SMS adapter;
- provider API credentials are server-side secrets only;
- SMS is attempted only after successful request commit and valid tracking code creation;
- SMS failure is logged/retried operationally and must not roll back the request or return fake failure to the customer;
- Telegram manager notification remains independent;
- no custom SMS admin panel is required for V1.
